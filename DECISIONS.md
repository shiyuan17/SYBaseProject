| DEC-20260608-001 | 2026-06-08 | AI memory layer | Maintain repo-local memory files in both backend and frontend repos; update them at task delivery time on demand. | Keeps durable context close to the code while avoiding noisy hook-enforced updates. | Future AI tasks must check and update memory files before final handoff. | If automatic agent dispatch or external memory sync is introduced. |
| DEC-20260608-002 | 2026-06-08 | Backend hooks | Use native backend hook scripts with PowerShell implementations and Git hook wrappers, not a Node hook manager. | Fits Maven/GitLab backend and avoids adding frontend tooling to the Java repo. | Hook maintenance lives under `scripts/hooks`; Windows PowerShell support is first-class. | If the team adopts a shared hook manager across repos. |
| DEC-20260608-003 | 2026-06-08 | Technical specimen registration pathology number editing | Completion accepts an optional `pathologyNo` candidate from the frontend; non-empty candidates must already match the selected application type rule and be unique, allowing the current case's own number. Empty candidates keep backend generation. | Avoids silent backend auto-completion of user-edited candidates while keeping final numbering authority server-side. | Invalid format returns 400 and duplicate occupied number returns 409; frontend previews are candidate-only and not persisted until completion. | If a dedicated pathology number reservation endpoint or different duplicate policy is introduced. |
| DEC-20260608-004 | 2026-06-08 | Slicing workstation print-before-slice flow | Slide printing is a backend-confirmed step via `POST /api/v1/slicings/slide-print`; `completeSlicing` requires printed slides and no longer creates slide numbers or accepts `slideCount`. | Physical slicing must operate on labels already generated/printed for the embedding box, and adjacent merge must happen before printing. | `slicings.task_id` links generated print records to the exact technical task; workbench statistics/lists are split into pending print, pending slice, and completed lists, filtered by `applications.application_type`. | If repeated print/merge, print rollback, or separate slide-label reservation semantics are introduced. |
| DEC-20260608-004 | 2026-06-08 | Tracking and abnormal application list pathology number display | Expose `pathologyNo` directly on `GET /api/v1/applications` list items instead of requiring frontend detail fan-out. | Keeps tracking lists performant and gives the backend one authoritative source for application-to-case pathology number display. | `ApplicationListItemResponse` and related query records include `pathologyNo`; `null` means no pathology case has been generated yet. | If application lists need pathology-number filtering or multiple active cases per application. |
| DEC-20260608-005 | 2026-06-08 | Historical-status lookup for workflow workstations | Preserve default current-stage filtering, but treat explicit business-key queries as historical lookups: `GET /api/v1/technical-tasks/pending?includeAllStatuses=true` may return completed tasks, and `GET /api/v1/specimen-outbounds` with `applicationId`, `specimenNo`, or exact specimen-number-or-barcode `identifier` may return rows outside outbound-ready status. | Frontend users need to retrieve old rows by exact identifiers while ordinary worklists must not suddenly expand to all historical data. Barcode scanners should behave like text input plus Enter while preserving outbound review before submit. | Frontend sibling `../SYBaseProjectWeb` keeps ordinary entry empty for affected pages and gates operations by status; outbound scan/Enter only queues a unique outbound-ready row and does not directly submit transport; backend defaults remain compatible for existing callers that omit the new flags/conditions. | If dedicated history endpoints replace pending/outbound list reuse, if ordinary worklists are redefined to include history, or if outbound scanning should submit transport immediately. |
| DEC-20260608-006 | 2026-06-08 | Flyway sync against local/target DM schemas with repaired historical gaps | `scripts/migration/run-bl-center-flyway.*` defaults `BL_CENTER_FLYWAY_OUT_OF_ORDER=true`, and `BlCenterFlywayCliSupport` also honors `SPRING_FLYWAY_OUT_OF_ORDER`. | Existing DM schemas can contain repaired/deleted history rows while newer migrations are already applied; allowing out-of-order lets idempotent Java repair migrations such as `V75` be backfilled before applying later pending migrations. | Migration sync emits Flyway's reproducibility warning in out-of-order mode; strict validation can be restored by setting `BL_CENTER_FLYWAY_OUT_OF_ORDER=false` before running the script. | If production release policy forbids out-of-order backfill or migration versions are renumbered to remove repaired gaps. |
| DEC-20260609-001 | 2026-06-09 | M2 specimen check-in and transport operator identity | Current request users may submit check-in / transport create / transport outbound / quick outbound without `operatorVerificationToken` only when the request body operator user ID matches the current user; non-current selected operators still require the existing verification token. Specimen confirmation keeps the original verification-token requirement. | The authenticated request already proves the current user's identity, but cross-user operation still needs explicit verification. | DTOs keep `operatorVerificationToken` optional for these transport/check-in endpoints; controllers must not silently trust arbitrary body operator IDs when token is blank. | If product requires re-authentication for every current-user operator action. |
| DEC-20260609-002 | 2026-06-09 | M2 specimen barcode binding semantics | Registering specimens without an explicit barcode stores `specimens.barcode = null`; `POST /api/v1/specimens/{specimenId}/barcode-binding` is the first-write operation for `targetBarcode`. | Barcode binding is an explicit operator workflow, not an automatic registration side effect. | DEC-20260609-003 | 2026-06-09 | M3 embedding confirmation workflow | `POST /api/v1/embeddings/start` is the confirmation action and persists `EMBEDDING_CONFIRM_PENDING`; `POST /api/v1/embeddings/cancel` may return only that middle state to `PENDING`; `POST /api/v1/embeddings/complete` is the only final-completion action that writes `COMPLETED` and creates downstream slicing tasks. Legacy `IN_PROGRESS` embedding tasks remain completable but are not cancellable through the rollback endpoint. | 包埋确认 and 包埋完成 are distinct business states, slicing must not receive work before final completion, and operators need a correction path before final embedding records exist. | Active embedding queries and timeout policy include `EMBEDDING_CONFIRM_PENDING`; embedding workstation summary pending counts include it, completed records do not; frontend sibling `../SYBaseProjectWeb` must show “包埋确认待完成”, enable “取消包埋” only for this state, and keep completion gated to this state or legacy `IN_PROGRESS`. | If a formal technical-task state machine replaces string status constants, product renames the middle status, or product allows cancelling final completed embedding records. |
