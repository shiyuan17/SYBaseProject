# M4 医生诊断与报告闭环规划

## 目标

- 在 `bl-center` 内完成“分片 -> 诊断 -> 医嘱 -> 审核签发 -> 报告修订 -> 科内会诊 -> 质控评价”的医生组核心闭环，承接 M3 染色出片后的病例输入。
- 让医生端形成“可分配、可诊断、可签发、可修订、可追溯”的正式报告主链路。
- 让医嘱状态可从医生端下达到技术端并回传，且让会诊、修订、质控统一进入审计轨迹。

## 本期范围

- 范围限定在 `bl-center` 内，不新增独立业务中心，不调整现有模块边界。
- 仅覆盖常规病理医生组主链路，不纳入冰冻、细胞学、液基细胞学、免疫组化、分子病理、外部收费集成和正式 PDF 渲染打印等后续能力。
- 承接 M3 输出的病例、标本、蜡块、玻片、技术质控结果和 `workflow_events`，继续以统一轨迹模型承载全链路追溯。
- 本期最小交付对象包括：
  - `DiagnosticTasks`
  - `PathologyReports`
  - `ReportVersions`
  - `ReportRevisionRequests`
  - `ConsultationCases`
  - `ConsultationParticipants`
  - `MedicalOrders`
  - `SlideQcEvaluations`
  - `WorkflowEvents`
  - `PdfSignatureConfigs`
- 本期最小接口组定义为：
  - `GET /api/v1/diagnostic-tasks/pending`
  - `POST /api/v1/diagnostic-tasks/{id}/assign`
  - `POST /api/v1/diagnostic-tasks/{id}/accept`
  - `POST /api/v1/diagnostic-tasks/{id}/start`
  - `GET /api/v1/pathology-cases/{id}/diagnostic-workbench`
  - `POST /api/v1/pathology-reports`
  - `POST /api/v1/pathology-reports/{id}/save-draft`
  - `POST /api/v1/pathology-reports/{id}/submit`
  - `POST /api/v1/pathology-reports/{id}/review`
  - `POST /api/v1/pathology-reports/{id}/reject`
  - `POST /api/v1/pathology-reports/{id}/sign`
  - `POST /api/v1/pathology-reports/{id}/publish`
  - `POST /api/v1/pathology-reports/{id}/delay-publish`
  - `POST /api/v1/report-revision-requests`
  - `POST /api/v1/report-revision-requests/{id}/approve`
  - `POST /api/v1/report-revision-requests/{id}/reject`
  - `POST /api/v1/medical-orders`
  - `POST /api/v1/medical-orders/{id}/cancel`
  - `GET /api/v1/medical-orders/pending`
  - `POST /api/v1/consultations`
  - `POST /api/v1/consultations/{id}/complete`
  - `POST /api/v1/slide-qc-evaluations`
  - `GET /api/v1/pathology-cases/{id}/report-tracking`
- 保留现有 M1/M2/M3 已发布接口、基础主数据和编号服务能力，不在 M4 内引入新的编号中心或新的跨模块编排中心。

## 实现说明

### 总体原则

- `bl-center` 继续作为唯一真实业务中心，M4 在现有 DDD 四层结构内扩展医生组流程，不额外拆分新模块。
- 医生工作台只消费聚合病例视图，不直接暴露底层多表拼装细节。
- 所有诊断、审核、签发、修订、会诊、医嘱、质控关键动作都必须写入 `workflow_events`，至少记录节点、动作、状态变化、操作人、终端和异常信息。
- 报告必须保留版本链，不允许覆盖已签发或已发布历史版本。
- 医嘱、会诊、修订、拒签、回退都必须通过显式业务动作流转，不允许直接手工改状态。

### 任务池与状态机

- M3 染色出片完成后自动投递 `diagnostic_tasks`，作为 M4 医生待办入口。
- 诊断任务最小状态建议为：
  - `PENDING`
  - `ASSIGNED`
  - `ACCEPTED`
  - `IN_PROGRESS`
  - `COMPLETED`
  - `CANCELLED`
  - `RETURNED`
- 病例主状态按最小医生链路推进：
  - `STAINING_COMPLETED -> DIAGNOSIS_PENDING -> DIAGNOSING -> REPORT_PENDING_REVIEW -> REPORT_REVIEWING -> REPORT_SIGNED -> REPORT_PUBLISHED`
- 报告状态最小建议为：
  - `DRAFT`
  - `SUBMITTED`
  - `REVIEWED`
  - `SIGNED`
  - `PUBLISHED`
  - `WITHDRAWN`
- 一个节点完成后，不直接越过任务状态机调用下游工作站逻辑，而是：
  - 更新当前任务或报告实体状态
  - 写入 `workflow_events`
  - 关闭当前待办或标记完成
  - 投递下一节点待办或状态占位
- 修订后不覆盖原版本，而是生成新版本并更新当前有效报告。

### 分片工作站

- 分片工作站作为医生任务分派入口，不承担报告编辑职责。
- `GET /api/v1/diagnostic-tasks/pending` 统一提供诊断待办查询入口，至少支持按病理号、病例号、紧急程度、时限、送检科室、是否会诊、是否修订和日期区间分页查询。
- `POST /api/v1/diagnostic-tasks/{id}/assign` 支持手工指定责任医生、初诊医生、审核医生，并记录派发人、派发时间和派发方式。
- 本期默认先支持人工分派，自动轮转只保留字段和后续扩展位，不纳入本期验收。

### 诊断工作台与病例聚合视图

- `GET /api/v1/pathology-cases/{id}/diagnostic-workbench` 作为诊断工作台聚合查询接口。
- 最小聚合内容包括：
  - 患者与送检信息
  - 临床诊断
  - 标本摘要
  - 蜡块玻片摘要
  - 技术质控结果
  - 历史病理
  - 当前报告草稿
  - 报告痕迹
  - 会诊、医嘱、修订标记
- 支持通过扫码、病理号或病例号快速进入工作台，但接口仍按病例聚合资源建模。
- 本期只规划常规病理诊断工作台，不展开显微镜设备控制、复杂图像采集协议和图像智能分析引擎。

### 报告编辑与版本链

- `POST /api/v1/pathology-reports` 用于创建首份报告草稿，绑定 `case_id` 与 `task_id`。
- `POST /api/v1/pathology-reports/{id}/save-draft` 支持多次暂存，更新当前草稿但不生成历史版本。
- `POST /api/v1/pathology-reports/{id}/submit` 用于提交审核，提交后进入审核流并冻结提交快照。
- `pathology_reports` 保存当前有效报告；`report_versions` 只在签发、发布、修订批准后形成正式版本快照。
- 报告编辑能力本期至少支持：
  - 暂存
  - 提交
  - 回退
  - 拒签
  - 延迟发布
  - 修订留痕
- 报告编号沿用现有编号服务能力，不在 M4 单独引入新的报告编号中心。

### 审核、签发与发布

- 初诊、审核、签发采用三级职责，不要求单一接口同时完成三步。
- `POST /api/v1/pathology-reports/{id}/review` 只允许审核医生操作，审核通过后更新报告与任务状态。
- `POST /api/v1/pathology-reports/{id}/reject` 用于审核退回，必须写入退回原因，并将任务退回诊断医生继续编辑。
- `POST /api/v1/pathology-reports/{id}/sign` 只允许签发医生操作，签发前必须校验报告已审核通过。
- `POST /api/v1/pathology-reports/{id}/publish` 与 `POST /api/v1/pathology-reports/{id}/delay-publish` 分开设计，以满足延迟发布场景。
- PDF 签名能力本期只规划到 `pdf_signature_configs`、签发记录和权限约束，不展开 PDF 渲染排版和打印细节实现。

### 医嘱闭环

- 医嘱从医生工作台开立，至少支持 `补片`、`重切`、`深切`、`特染`、`免疫组化占位` 这类病理场景。
- `medical_orders` 保存医嘱主记录，最小状态建议为：
  - `PENDING`
  - `IN_PROGRESS`
  - `COMPLETED`
  - `CANCELLED`
- `POST /api/v1/medical-orders` 负责开立医嘱，`POST /api/v1/medical-orders/{id}/cancel` 负责取消未完成医嘱，`GET /api/v1/medical-orders/pending` 负责待执行医嘱查询。
- 本期重点落地“医生端下达 -> 技术端接收执行 -> 状态回传诊断端”的主链路。
- 收费状态本期只保留 `billing_status` 字段和占位约束，不把真实收费系统对接纳入 M4 完成交付。

### 科内会诊

- 只把科内会诊作为 M4 必做闭环，外院会诊保留结构扩展位但不作为上线前置条件。
- `consultation_cases` 与 `consultation_participants` 记录发起人、参与人、参与角色、意见、已读状态和代写信息。
- `POST /api/v1/consultations` 用于发起会诊，`POST /api/v1/consultations/{id}/complete` 用于完成会诊并固化会诊意见。
- 会诊完成后可回流到当前诊断或报告修订流程，并写入病例轨迹。

### 报告修订与质控评价

- `report_revision_requests` 负责修订申请、审批、驳回和批准后的新版本关联。
- 修订必须基于已签发或已发布报告发起，不允许直接修改历史版本正文。
- `POST /api/v1/report-revision-requests` 用于发起修订申请，`approve` 和 `reject` 用于审批流转。
- 修订审批通过后，基于当前有效报告生成新版本并更新 `pathology_reports.version_no`。
- 质控评价沿用 `slide_qc_evaluations`，补充医生端录入入口。
- `POST /api/v1/slide-qc-evaluations` 至少支持录入评价结果、问题描述、改进建议和评价人信息。
- 质控不合格时可触发医嘱或返工建议，但本期默认不把返工编排重新纳入 M4 主文档中心，仍由 M3 流程承接。

### 轨迹、通知与权限

- `GET /api/v1/pathology-cases/{id}/report-tracking` 作为报告闭环追踪聚合查询接口，最小返回内容包括：
  - 病例基础信息
  - 诊断任务状态
  - 当前报告状态
  - 修订链
  - 会诊链
  - 医嘱链
  - 关键时间线事件
  - 异常与审批标记
- 报告修订相关通知沿用现有消息主题能力，复用 `TOPIC_REPORT_REVISION`。
- M4 需补充医生组专属权限码、角色绑定和测试用户种子，但本次规划不展开到角色矩阵明细，只要求覆盖：
  - 分片
  - 诊断
  - 审核
  - 签发
  - 修订审批
  - 会诊
  - 质控

## 测试与验收

- M4 验收场景至少覆盖：
  - 正常主链路：M3 染色完成后自动生成诊断待办，完成分派、诊断、提交、审核、签发、发布，最终可查询正式报告和完整轨迹。
  - 暂存与回退：报告草稿多次暂存，提交后被审核退回，重新编辑后再次提交并通过。
  - 延迟发布：报告已签发但延迟发布，到期后可进入已发布状态。
  - 修订闭环：已发布报告发起修订申请，经审批后生成新版本，原版本仍可追溯。
  - 医嘱闭环：医生开立医嘱后技术端可见并处理，诊断端能看到执行中和完成状态。
  - 会诊闭环：发起科内会诊、参与人录入意见、会诊完成并回流到报告决策。
  - 质控联动：医生录入玻片质控评价，不合格场景能留下问题描述并触发后续处理依据。
  - 权限约束：初诊、审核、签发、修订审批分别校验越权失败。
  - 审计追溯：关键动作均能在 `workflow_events` 或报告版本链中回放。
- 推荐的实现验证分层为：
  - 应用服务集成测试覆盖分派、诊断、审核签发、修订、医嘱和会诊主链路
  - 接口集成测试覆盖权限、分页查询、状态约束、异常返回和聚合视图
  - 数据持久化验证覆盖报告版本链、修订关联、医嘱回传和轨迹查询
- 完成标志：
  - 染色出片后的病例可稳定流转到正式报告发布
  - 报告、修订、会诊和医嘱可全程追溯当前状态与操作记录
  - 关键审核、签发、修订分支可闭环

## 当前默认与后续建议

- M4 默认只规划常规病理医生组主链路，不纳入冰冻、细胞学、液基细胞学、免疫组化、分子病理、外院会诊和真实收费集成等扩展能力。
- M4 默认继续以 `bl-center` 作为唯一真实业务中心，不拆分新的医生工作台中心、报告中心或任务编排中心。
- M4 默认以 `docs/database/病理基础数据表.sql` 作为数据模型参考来源，但只承诺最小闭环所需实体，不要求一次性落全量病理数据库草案。
- M4 默认科内会诊纳入本期闭环，外部会诊只保留结构扩展位。
- M4 默认自动分片、模板智能推荐、显微镜深度设备联动仅作为后续建议，不写入本期验收承诺。
- 后续实现建议优先拆分医生段应用服务职责，避免把分片、诊断、报告、修订、医嘱和会诊持续堆积在单一应用服务类中。
