核心发现

Critical

提交配置中带有默认数据库密码与默认 JWT 密钥，生产配置还允许自动生成密钥

认证中心和业务中心都把默认数据库密码、默认 SM2 私钥/公钥直接放进了版本库配置；同时生产配置把 allow-generated-keys 设为 true，运行时守卫只在该开关关闭时才强制要求显式密钥。这会把“未配置安全参数”的问题降级成“静默使用仓库默认值或本地生成值”，属于高风险配置缺陷。

Required

技术待办任务的“先查再写” upsert 存在并发竞争窗口，可能产生重复待办

upsertTechnicalPendingTask 先 select count(1)，再根据结果决定 update 或 insert。在并发请求同时为同一个 caseId 执行时，两个线程都可能读到 0，然后各自插入一条 PENDING 任务，形成重复待办或需要后续人工清理的数据脏写。

证据位置 说明
bl-center/src/main/java/com/company/bl/infrastructure/persistence/JdbcSpecimenWorkflowTransportMutationSupport.java:230-269 读取数量与插入写入之间没有唯一约束、锁或数据库原子 upsert。

建议：给活跃任务建立唯一索引，或改成数据库原子 upsert / merge；至少要把“存在性判断”和“写入”收敛到单条 SQL 或明确事务锁中。

Watch

登录失败保护仅在单节点内存中生效，并且失败状态没有主动清理策略

LoginAttemptGuard 用本地 ConcurrentHashMap 保存失败状态。这样一来，多实例部署时限流可以被轮询不同节点绕过；另一方面，未达到封禁阈值且后续不再重试的键会常驻内存，项目运行越久，状态表越容易积累无意义条目。

证据位置 说明
auth-center/src/main/java/com/company/auth/application/service/LoginAttemptGuard.java:16 状态直接保存在进程内 ConcurrentHashMap。
auth-center/src/main/java/com/company/auth/application/service/LoginAttemptGuard.java:44-71 只在成功登录或“再次访问且恰好过期”时清理状态，没有统一过期淘汰机制。

建议：把登录保护迁移到 Redis 之类的共享存储，至少补上 TTL / 定时清理策略，并明确多实例部署下的行为预期。
