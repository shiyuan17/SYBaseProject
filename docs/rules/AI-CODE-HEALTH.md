# AI 健康度开发规范

## 目标与适用范围

本规范约束 AI（Codex、Claude、Cursor、Copilot 等）在本仓库生成 Java 代码时的行为，目标是持续产出易理解、易维护、易测试、易扩展、易审查的代码。所有规则服务于**降低认知负担**，不是机械满足条文。

- 与 `CODING_RULES.md` 的关系：本文件是质量自检附录；编码基线、验证命令与“何时必须补测试”以 `CODING_RULES.md` 为准
- 与 CI 的关系：`scripts/ci/generate-code-health-checklist` 系列脚本以本文件为规则来源生成健康度报告；报告仅作治理证据，不替代测试

## 基本准则

- 显式优于隐式；清晰优于聪明；稳定优于炫技
- 可理解性优于代码行数；可维护性优于设计模式堆砌
- 优先直白实现与新人可读性，不写炫技代码、不为减少行数降低可读性、不制造无业务意义的中间层

## 规则速查表

### 1. 函数健康度

| 规则 | 要点 | 反例信号 |
| --- | --- | --- |
| 单一职责 | 一个方法只负责一件事 | 一个方法同时做校验 + 计算 + 持久化 + 通知 |
| 单一抽象层级 | 业务编排不混入 SQL、消息发送、日志落盘等实现细节 | service 方法里手拼 SQL、直接发 MQ |
| 无副作用 | 不修改入参、不改全局/静态状态；优先返回新对象 | `order.setStatus(...)` 在校验方法里顺手改状态 |
| 可独立测试 | 可单独调用、独立验证、无环境依赖 | 必须起容器/连库才能测一个纯计算 |
| 行数参考 | 业务编排 ≤ 30 行、算法 ≤ 60 行；行数是参考不是目标 | 为凑行数做形式主义拆分，阅读时不断跳转 |

### 2. 命名

| 规则 | 要点 |
| --- | --- |
| 业务意图 | 禁止缩写、自造术语、模糊表达；命名直接体现业务含义 |
| 方法命名 | 动词 + 名词：`createOrder`、`calculatePrice`、`validateSpecimen` |
| 布尔命名 | `is` / `has` / `should` / `can` 前缀：`isPaid`、`canDelete` |
| 事件命名 | 过去式：`OrderCreated`、`ReportSigned` |
| 禁用名 | `data`、`info`、`tmp`、`flag`、`obj`、`res`、`result1`、`testData` |

### 3. 类型与契约

| 规则 | 要点 |
| --- | --- |
| 显式类型 | 公共方法签名类型完整；不依赖裸 `Object` / 原始类型集合传递结构数据 |
| 入参集中 | 参数超过 3 个时收敛为 Command / Query / Request 对象 |
| 出参明确 | 返回明确的 Result / DTO 类型，不返回 `Map<String, Object>` 之类不确定结构 |
| 校验前置 | 入口统一用 Bean Validation（`jakarta.validation`）或显式校验器，不散落 if 判空 |
| 分层契约 | DTO / 领域对象 / 持久化对象不互相透传，转换显式可见（详见 `DDD_RULES.md`） |

### 4. 错误处理

| 规则 | 要点 |
| --- | --- |
| 禁止吞异常 | 不允许空 catch、catch 后仅打印继续；异常要么处理要么向上抛 |
| 结构化错误 | 业务失败抛带错误码的业务异常，不抛字符串、不滥用 `RuntimeException` |
| 错误分类 | 用户输入错 → 4xx；权限 → 403；不存在 → 404；业务规则失败 → 业务错误码；系统异常 → 日志 + 告警 |
| 日志安全 | 患者/报告等敏感字段不进日志与异常信息（详见 Security 相关规则） |

### 5. 状态与依赖

| 规则 | 要点 |
| --- | --- |
| 显式依赖 | 依赖通过构造器注入，禁止隐藏单例、静态可变状态、`ThreadLocal` 滥用 |
| 副作用可追踪 | 写库、发消息、写文件等副作用集中在编排层，可从方法签名与调用链看出 |

### 6. 文件与目录

| 规则 | 要点 |
| --- | --- |
| 单一主题 | 一个文件只负责一个主题；按领域语义命名 |
| 禁用名 | 不新增 `Utils`、`Common`、`Helper`、`Tools` 类垃圾场文件；既有的不再扩容 |
| 文件健康 | 文件行数与结构热点以 CI 文件健康门禁与 `largest-files-report` 为准 |

### 7. 测试与可验证性

- 优先写测试再写实现；测试断言业务行为（`shouldCreateOrder`），不断言实现细节（调用次数）
- 核心逻辑必须覆盖业务规则、边界条件、异常路径
- 强制触发条件（何时必须补测试）以 `CODING_RULES.md` 为准

## 交付前自检清单

- [ ] 每个新增/修改方法能一句话说明作用，且只负责一件事
- [ ] 无混合抽象层级、无隐藏副作用、无修改入参
- [ ] 命名表达真实业务含义，无缩写、无禁用名
- [ ] 公共签名类型完整，入参/出参结构明确
- [ ] 无空 catch、无字符串异常、错误分类正确、敏感字段不进日志
- [ ] 依赖显式注入，无新增全局可变状态
- [ ] 文件主题单一，未新增垃圾场文件
- [ ] 业务规则、边界、异常路径有测试，断言面向行为
- [ ] 新人能在 30 秒内看懂主要改动，无无意义抽象与跳转阅读

## 健康度评分模型

CI 健康度报告按以下权重评分，仅作治理参考：可读性 30%、命名质量 20%、测试能力 20%、类型完整性 15%、错误处理 15%。90+ 优秀 / 80+ 良好 / 70+ 合格 / 60+ 需优化 / 低于 60 建议重构。
