# M3 技术组核心生产线闭环规划

## 目标

- 在 `bl-center` 内完成“病理接收后待办 -> 取材描写 -> 脱水 -> 包埋 -> 常规切片 -> 染色出片”的常规病理技术主链路。
- 承接 M2 已落地的 `technical_pending_tasks`，以技术待办池作为 M3 流程入口，首个待办类型固定为 `GROSSING`。
- 让蜡块、玻片、技术质控、返工任务和流程轨迹可全程追踪，形成技术组核心生产线闭环。
- 在不拆分新业务中心的前提下，为后续 M4 医生诊断与报告闭环提供稳定、可追溯的技术段输入。

## 本期范围

- 范围限定在 `bl-center` 内，不新增新的业务中心，不调整现有模块边界。
- 仅覆盖常规病理技术主链路，不纳入细胞学、液基细胞学、免疫组化、分子病理、特检医嘱、收费、归档、报告签发等后续能力。
- 承接 M2 接收成功后的病例与标本数据，继续复用 `workflow_events` 作为全链路轨迹表，继续复用 `technical_pending_tasks` 作为技术待办入口，不新增总控表。
- 本期最小交付对象包括：
  - `Samplings`
  - `SamplingBlocks`
  - `DehydrationBatches`
  - `DehydrationBatchItems`
  - `Embeddings`
  - `EmbeddingBoxes`
  - `Slicings`
  - `Slides`
  - `SlideStainings`
  - `ReworkOrders`
  - `SlideQcEvaluations`
  - `WorkflowEvents`
  - `CaseMediaAssets`
- 本期最小接口组定义为：
  - `GET /api/v1/technical-tasks/pending`
  - `POST /api/v1/grossings/start`
  - `POST /api/v1/grossings/complete`
  - `POST /api/v1/dehydration-batches`
  - `POST /api/v1/dehydration-batches/{id}/start`
  - `POST /api/v1/dehydration-batches/{id}/complete`
  - `POST /api/v1/embeddings/start`
  - `POST /api/v1/embeddings/complete`
  - `POST /api/v1/slicings/start`
  - `POST /api/v1/slicings/complete`
  - `POST /api/v1/slide-stainings/start`
  - `POST /api/v1/slide-stainings/complete`
  - `POST /api/v1/rework-orders`
  - `POST /api/v1/rework-orders/{id}/execute`
  - `GET /api/v1/pathology-cases/{id}/technical-tracking`
- 保留现有 M1/M2 已发布接口及编号服务，不在 M3 内引入新的编号中心或新的跨模块编排中心。

## 实现说明

### 总体原则

- `bl-center` 继续作为唯一真实业务中心，M3 在现有 DDD 四层结构内扩展技术流程，不额外拆分新模块。
- 技术任务统一进入任务池，通过状态机驱动流转，工作站之间不得直接互调或绕过任务池写下游数据。
- 所有关键节点必须写入 `workflow_events`，至少记录节点、动作、状态变化、操作人、终端和异常信息。
- 返工、退回、重做必须保留原始记录，不允许直接覆盖历史处理痕迹。
- 设备接入统一经适配层处理，工作站服务内不直接耦合打印机、打号机、高拍仪或其它设备协议。

### 任务池与状态机

- M2 接收成功后已写入 `technical_pending_tasks`；M3 以该表作为技术主链路起点，首个待办类型固定为 `GROSSING`。
- 病例主状态按最小技术链路推进：
  - `RECEIVED -> SAMPLING -> DEHYDRATION -> EMBEDDING -> SLICING -> STAINING`
- 技术待办最小状态建议为：
  - `PENDING`
  - `IN_PROGRESS`
  - `COMPLETED`
  - `RETURNED`
  - `CANCELLED`
- 一个节点完成后，不直接调用下游工作站逻辑，而是：
  - 更新当前节点实体状态
  - 写入 `workflow_events`
  - 关闭当前待办
  - 投递下一节点待办
- `GET /api/v1/technical-tasks/pending` 统一提供技术待办查询入口，至少支持按节点、状态、病例号、病理号、日期区间分页查询。

### 取材描写

- `POST /api/v1/grossings/start` 用于领取或开始取材任务，更新待办与病例状态为 `SAMPLING` 在制。
- `POST /api/v1/grossings/complete` 用于完成取材描写，最小行为包括：
  - 创建或更新 `samplings`
  - 生成 `sampling_blocks`
  - 为每个材块预关联包埋盒号
  - 记录大体描述、取材人、取材时间
  - 可选写入大体拍照附件到 `case_media_assets`
- 取材模板优先复用已有主数据与模板能力，以“模板匹配 + 人工调整”为原则，不在本期引入独立智能引擎。
- 材块编号沿用现有 `NumberingService.generateBlockNo(caseId)`，保持病例内唯一。
- 取材完成后关闭 `GROSSING` 待办，并按材块或包埋盒维度投递脱水待办。

### 脱水

- `POST /api/v1/dehydration-batches` 负责创建脱水批次，维护 `dehydration_batches` 与 `dehydration_batch_items`。
- `POST /api/v1/dehydration-batches/{id}/start` 用于装篮上机，记录批次号、脱水篮号、设备号、上机时间与操作人。
- `POST /api/v1/dehydration-batches/{id}/complete` 用于完成脱水，最小约束包括：
  - 仅允许已装篮的包埋盒或材块进入完成态
  - 脱水完成后才允许进入包埋
  - 必须写入 `workflow_events`
- 本期允许两种装篮模式：
  - 按预生成包埋盒装篮
  - 按 `sampling_blocks` 装篮
- 脱水节点仅纳入“批次拍照归档”这一类影像能力，照片通过 `case_media_assets` 关联批次对象，不单独建设媒体中心。

### 包埋

- `POST /api/v1/embeddings/start` 用于开始包埋任务，要求对应材块或包埋盒已经完成脱水。
- `POST /api/v1/embeddings/complete` 用于完成包埋，最小行为包括：
  - 创建或更新 `embeddings`
  - 创建或更新 `embedding_boxes`
  - 记录包埋人、包埋时间、材块数量、切片注意事项
  - 写入包埋环节轨迹事件
- 包埋盒应满足以下追溯要求：
  - 能回溯到病例、标本、取材记录、取材块
  - 能关联下游切片与返工记录
- 包埋完成后才允许进入切片；若质控判定需要重取材或重包埋，应通过返工单回流，不直接改写原包埋结果。

### 常规切片

- `POST /api/v1/slicings/start` 用于开始切片任务，要求关联的包埋盒已完成包埋。
- `POST /api/v1/slicings/complete` 用于完成切片，最小行为包括：
  - 创建或更新 `slicings`
  - 生成 `slides`
  - 记录切片数量、切片人、切片时间
  - 记录切片备注、特殊要求和注意事项
  - 写入跳号、遗漏、重切提醒信息
- 玻片号沿用现有 `NumberingService.generateSlideNo()`，保持全局唯一。
- 切片完成后关闭切片待办，并为玻片生成染色待办。
- 如对接玻片打号机，失败不得回滚已完成的切片主业务记录，但必须记录异常轨迹与重试标记。

### 染色出片

- `POST /api/v1/slide-stainings/start` 用于开始染色任务，要求对应玻片已创建且处于待染色状态。
- `POST /api/v1/slide-stainings/complete` 用于完成染色出片，最小行为包括：
  - 创建或更新 `slide_stainings`
  - 记录染色类型、染色状态、出片时间、操作人
  - 更新玻片状态为已染色可用
  - 写入流程轨迹与异常标记
- `slide-stainings complete` 后病例主状态更新为 `STAINING` 完成态，视为 M3 主链路到达出片终点。
- 染色工作站应支持按病例聚合同一患者多张玻片的批量操作，但接口仍按资源建模，不按页面动作暴露。

### 返工与质控

- 返工统一通过 `POST /api/v1/rework-orders` 创建，通过 `POST /api/v1/rework-orders/{id}/execute` 执行，不直接覆盖原节点数据。
- `rework_orders` 最小支持以下回流类型：
  - 回流到 `SAMPLING`，处理重取材
  - 回流到 `EMBEDDING`，处理重包埋
  - 回流到 `SLICING`，处理重切、深切、补片
  - 回流到 `STAINING`，处理重染
- 返工执行后必须：
  - 保留原始记录
  - 写入返工前后轨迹
  - 重新生成对应节点待办
- 玻片质控最小复用 `slide_qc_evaluations`，评价结果至少支持：
  - `PASS`
  - `FAIL`
  - `REWORK_REQUIRED`
- 本期质控退回以包埋质控、切片质控为主；若判定不合格，需要通过返工单把任务退回上游节点，而不是直接手工改状态。

### 轨迹/影像/设备接入

- `GET /api/v1/pathology-cases/{id}/technical-tracking` 作为技术追踪聚合查询接口，最小返回内容包括：
  - 病例基础信息
  - 当前主状态
  - 标本摘要
  - 材块摘要
  - 玻片摘要
  - 技术待办状态
  - 时间线事件
  - 异常与返工标记
- 影像能力本期只纳入：
  - 取材大体拍照
  - 脱水批次拍照
- 工作站与设备的边界如下：
  - 打印机用于标签或单据打印
  - 打号机用于包埋盒或玻片编码打印
  - 高拍仪用于取材或脱水环节的图像采集
- 上述设备全部通过适配层接入，应用服务只处理统一结果，不直接处理设备厂商协议、串口、驱动或本地命令。

## 测试与验收

- M3 验收场景至少覆盖：
  - 正常主链路：接收病例进入待办，完成取材、脱水、包埋、切片、染色，最终可查询完整技术轨迹。
  - 多标本场景：同一病例下多个标本分别取材、分别出块，最终能汇总到同一病例追踪视图。
  - 返工闭环：重取材、重包埋、重切、重染各至少一条链路，且原始记录仍可追溯。
  - 质控退回：包埋或切片质控不合格后退回上游节点，任务重新进入对应待办池。
  - 漏项与跳号提醒：切片与染色阶段触发提醒，但不丢失当前任务上下文。
  - 编号与追溯：蜡块号、玻片号唯一，且都能回溯到病例、标本、取材块。
  - 设备适配容错：打印或打号失败不回滚主业务记录，但必须写入轨迹和异常标记。
  - 超时提醒：取材、脱水、染色至少三类任务支持超时识别和待办筛出。
- 推荐的实现验证分层为：
  - 应用服务集成测试覆盖主链路、返工、质控退回
  - 接口集成测试覆盖权限、分页查询、状态约束、异常返回
  - 数据持久化验证覆盖实体落库关系、唯一约束与追溯查询
- 完成标志：
  - 接收病例可稳定流转到染色出片
  - 蜡块和玻片可全程追溯来源标本、当前状态和操作记录
  - 关键返工分支可闭环

## 当前默认与后续建议

- M3 默认只规划常规病理技术主链路，不纳入细胞学、液基细胞学、免疫组化、分子病理、特检医嘱等扩展能力。
- M3 默认继续以 `bl-center` 作为唯一真实业务中心，不拆分新的技术流程中心或任务编排中心。
- M3 默认以 `docs/database/病理基础数据表.sql` 作为数据模型参考来源，但只承诺最小闭环所需实体，不要求一次性落全量病理数据库草案。
- M3 默认沿用 M2 的权限建设方式，后续需补充 M3 工作站权限、角色与测试用户种子，但本次规划不展开到角色矩阵明细。
- M3 默认不纳入收费、归档、医生诊断、报告签发、外院会诊、冰冻追加常规等后续阶段内容。
- 后续实现建议优先拆分 `SpecimenWorkflowAppService` 的技术段编排职责，按工作站和读写职责逐步拆出独立应用服务，避免继续堆积在单一服务类中。
