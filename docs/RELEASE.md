# RELEASE.md — 版本发布与回滚规范

## 目标与适用范围

本文件定义项目的版本策略、环境约束、发布步骤、质量门禁与回滚要求。

- 适用对象：研发、测试、运维、发布负责人、AI 助手
- 适用范围：版本发布、热修复、环境部署、回滚处理、发布材料准备
- 规范定位：聚焦“如何上线与回滚”；分支命名、PR、提交与合并规范以 `GIT_RULES.md` 为准

## 强制规则

### 1. 版本策略

- 统一采用 `SemVer`：`MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]`
- `MAJOR`：不兼容 API 或数据库变更
- `MINOR`：向后兼容的新功能
- `PATCH`：缺陷修复、安全补丁、低风险优化

版本示例：

- `1.0.0`
- `1.2.0`
- `1.2.3`
- `2.0.0-rc.1`

### 2. 环境基线

| 环境 | 用途 | 部署策略 | 数据要求 |
|------|------|----------|----------|
| `dev` | 开发自测 | 高频部署 | 可使用共享开发数据 |
| `test` | QA 测试 | 随集成变更部署 | 可重置测试数据 |
| `staging` | UAT / 预发布验证 | 仅候选版本部署 | 使用脱敏生产副本 |
| `prod` | 线上服务 | 仅正式版本部署 | 使用生产数据 |

强制要求：

- 生产环境敏感配置必须来自环境变量、密钥平台或配置中心
- `staging` 必须具备与生产接近的依赖拓扑
- 生产发布前必须确认数据库、缓存、消息队列、对象存储配置已就绪
- `staging` 或专用信创环境必须完成一次候选版本的全链路兼容验证

### 3. 标准发布流程

标准版本发布必须按以下顺序执行：

1. 从 `develop` 创建 `release/*` 分支，命名与流程遵循 `GIT_RULES.md`
2. 更新版本号、变更日志、发布说明
3. 执行 CI、回归测试、UAT 验证
4. 执行信创环境验证并更新兼容矩阵、例外审批记录
5. 审核数据库迁移、配置变更、兼容性影响
6. 将发布分支合并到 `main` 并打 Tag
7. 同步回 `develop`
8. 触发生产部署
9. 验证健康检查、核心链路、监控与告警

### 4. 热修复流程

- 热修复必须从 `main` 创建 `hotfix/*` 分支
- 仅允许修复线上阻断问题，不得夹带需求开发
- 版本号至少递增 `PATCH`
- 合并完成后必须同步回 `develop`

### 5. 质量门禁

正式发布前必须全部满足：

- 单元测试、集成测试全部通过
- 关键业务回归完成并有记录
- 覆盖率、静态检查、依赖漏洞扫描达到团队门禁
- 新增数据库脚本已在 `staging` 验证
- 新增或变更接口已同步文档并完成消费者确认
- 信创环境验证通过，兼容矩阵、例外审批、替代方案状态已更新
- 发布、回滚负责人明确，沟通通知完成

### 6. 回滚要求

满足以下任一条件时立即评估回滚：

- 核心交易、认证、登录、下单、支付等能力不可用
- 错误率、超时率、资源占用显著高于基线
- 出现数据错写、重复消费、消息积压或不可逆数据污染风险
- 安全漏洞或权限绕过被发现

回滚必须覆盖两类内容：

- 应用回滚：恢复上一稳定版本镜像或部署单元
- 数据回滚：依赖已审核的回滚脚本、补偿脚本或人工处置方案

## 推荐实践

- 在 `release/*` 阶段冻结非必要功能变更，只接受发布阻断项修复
- 提前准备发布窗口、值班人、回滚责任人与验证清单
- 对重大版本做灰度、分批、可观测性增强与性能基线比对
- 发布说明同步包含接口变更、配置项变更、数据变更、兼容性影响
- 为数据库变更准备“前向修复”和“回滚补偿”两套方案
- 为国产环境保留镜像、驱动、部署脚本、回滚验证记录

## 反例/禁用项

- 在发布当天临时合入未验证的新需求
- 没有 `staging` 验证就直接执行生产迁移
- 把“CI 已通过”当作可以免掉 UAT 或发布检查的理由
- 没有数据回滚方案却执行破坏性结构变更
- 热修复分支里顺带处理重构、优化或不相关需求

## 检查清单

- [ ] 版本号、Tag、CHANGELOG、发布说明已更新
- [ ] 发布分支与合并流程符合 `GIT_RULES.md`
- [ ] CI、回归、UAT、依赖检查全部通过
- [ ] 数据库脚本、配置变更和兼容性影响已审核
- [ ] 信创兼容矩阵结果、例外审批、替代方案状态已确认
- [ ] 国产环境回滚验证已完成或已留档
- [ ] 发布窗口、通知、负责人、监控与告警已准备
- [ ] 回滚方案和验证步骤已确认
