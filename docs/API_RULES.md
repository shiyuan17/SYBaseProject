# API_RULES.md — 接口设计规范

## 目标与适用范围

本文件定义 REST API 的设计、实现、文档与兼容性规则。

- 适用对象：接口开发者、前后端协作者、测试人员、AI 助手
- 适用范围：HTTP API、OpenAPI 文档、Apifox 定义、接口测试
- 规范定位：统一接口风格、响应结构、错误语义与文档同步方式

## 强制规则

### 1. 路径与版本

- API 路径使用名词复数和小写短横线风格
- 统一前缀示例：`/api/v1/users`
- 版本升级必须通过显式版本号控制，不得 silently break
- 路径表达资源，查询参数表达过滤、排序、分页

### 2. 请求与响应模型

- 请求对象与响应对象必须独立定义
- 创建请求、更新请求、查询请求不得混用同一个 DTO
- 响应对象必须稳定，禁止直接暴露数据库实体或内部技术字段
- 时间、金额、状态等字段必须有统一格式约束

### 3. HTTP 语义

- `GET` 用于查询
- `POST` 用于创建或不可幂等动作
- `PUT` 用于整体更新
- `PATCH` 用于部分更新
- `DELETE` 用于删除或注销

常见状态码：

- `200` 成功
- `201` 创建成功
- `204` 删除成功无响应体
- `400` 参数错误
- `401` 未认证
- `403` 无权限
- `404` 资源不存在
- `409` 并发冲突或重复创建
- `500` 服务内部错误

### 4. 分页、过滤与排序

- 分页参数统一使用 `page`、`size`
- 排序参数统一使用 `sort`
- 过滤参数语义必须稳定，不得使用含糊字段名
- 大列表接口必须分页，禁止默认返回全量数据

### 5. 错误响应与幂等

- 错误响应必须包含 `code`、`message`、`traceId` 或等价追踪字段
- 客户端可修复错误与服务端错误必须区分
- 创建类接口如存在重试风险，必须定义幂等策略
- 幂等键、去重键或业务唯一约束需要文档化

### 6. 鉴权与文档同步

- 需要鉴权的接口必须明确权限模型、作用域或角色要求
- 对外接口变更必须同步 OpenAPI / Apifox
- 文档中的示例请求、示例响应、错误码必须与实现一致
- 涉及文件上传、导出、时间格式、字符编码、浏览器行为的接口，必须说明信创客户端兼容注意事项

统一错误响应示例：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "用户不存在",
  "traceId": "3f2d0d9b7f3f4f8f"
}
```

统一分页响应示例：

```json
{
  "items": [],
  "page": 1,
  "size": 20,
  "total": 0
}
```

## 推荐实践

- 用资源视角命名接口，避免动作式路径泛滥
- 对查询接口提供可组合但有限制的过滤能力
- 用明确错误码支持前端和调用方做稳定处理
- 为重要接口补充幂等、限流、超时和重试建议
- 在发布前做消费者兼容性确认，减少隐性破坏

## 反例/禁用项

- 使用 `/getUserList`、`/doCreate` 这类动作式路径
- 直接把数据库主表对象序列化后返回给前端
- 接口错误时只返回“操作失败”而没有错误码
- 同一字段在不同接口里含义不同
- 修改响应结构却不升级版本、不通知调用方、不更新文档

## 检查清单

- [ ] 路径、版本、HTTP 方法符合统一风格
- [ ] 请求和响应模型已分离
- [ ] 分页、排序、过滤规则清晰
- [ ] 错误响应、错误码、幂等策略已定义
- [ ] 鉴权要求和文档已同步
- [ ] 涉及上传、导出或编码行为的接口已补充信创客户端说明
- [ ] 示例请求与响应可直接用于联调
