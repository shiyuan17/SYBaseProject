# 病理全流程系统里程碑规划（研发落地版）

## 1. 文档目标

本文档用于将当前仓库内的病理功能规划整理为可执行的研发里程碑，作为产品、研发、测试、实施协同推进的统一基线。

规划原则：

- 以当前仓库现状为基础，默认继续在 `bl-center` 中沉淀病理核心业务能力。
- 按“先打通常规病理主闭环，再扩展支撑与优化能力”的顺序推进。
- 每个里程碑都必须满足“可演示、可测试、可上线试运行”的阶段出口要求。

## 2. 当前仓库基础

当前仓库已经具备以下基础：

- 根项目为 `Java 17 + Spring Boot 3 + Maven` 多模块工程。
- `bl-center` 已作为病理业务模块存在，并具备 `Application` 申请单基础能力。
- `common/*` 已提供通用核心、Web 和测试基础模块。
- `docs/detailed_list/` 已整理病理业务功能分解，可作为里程碑拆分依据。

当前默认实现边界：

- 主业务模块：`bl-center`
- 公共基础模块：`common/common-core`、`common/common-web`、`common/common-test`
- 非病理示例模块：`user-center`

## 3. 总体实施策略

建议总节奏为 `24-32 周`，拆分为 `7` 个里程碑。

优先顺序如下：

| 里程碑 | 建议周期 | 核心目标 | 阶段出口 |
|---|---:|---|---|
| M1 | 2-4 周 | 建立基础平台与主数据底座 | 权限、字典、编码、配置可复用 |
| M2 | 3-5 周 | 打通临床送检与标本接收闭环 | 申请到接收全程可追踪 |
| M3 | 4-6 周 | 建立技术组核心生产线 | 接收到出片主链路打通 |
| M4 | 4-6 周 | 建立医生诊断与报告闭环 | 可生成正式报告并签发 |
| M5 | 3-4 周 | 补齐归档与运营支撑 | 归档、借记、物资管理可用 |
| M6 | 4-5 周 | 完成集成、收费、统计、历史数据 | 融入医院外围系统 |
| M7 | 2-3 周 | 完成试点上线与稳定化 | 可在试点科室连续运行 |

## 4. 里程碑规划

### M1. 基础平台与病理主数据底座

目标：

- 建立所有工作站共用的身份、字典、编码和配置能力。

交付内容：

- 完成系统用户、角色权限、菜单或工作站授权、消息订阅授权。
- 完成部位字典、医嘱字典、医嘱套餐、检查号规则、通用配置管理。
- 完成描写模板管理、取材规范管理两套基础知识库。
- 统一病理号、申请单号、标本号、蜡块号、玻片号编码策略。
- 建立审计日志、操作留痕、状态流转枚举、基础字典缓存策略。

落地建议：

- 优先将权限、字典、编码规则沉淀为 `bl-center` 的共享应用能力。
- 仅在跨模块稳定复用后，再考虑下沉到顶层 `common/*` 或 `infrastructure/*`。
- 所有后续业务实体在设计时统一引用编码规则与字典项，不允许各流程自行维护一套编号逻辑。

完成标志：

- 新用户和角色可配置到具体工作站。
- 任一业务流程可引用统一字典与编号规则。
- 模板和规范库可被取材与诊断流程直接调用。

### M2. 临床送检与标本闭环

目标：

- 打通“临床申请 -> 标本采集 -> 固定核对 -> 转运 -> 病理接收”的前半闭环。

交付内容：

- 扩展 `Application`，新增患者、申请、标本、固定记录、转运单、接收记录等核心实体。
- 落地病理申请工作站、标本采集登记、标本固定核对、标本转运、标本接收。
- 支持二维码或条码标识、标签打印、未固定与未接收提醒、拒收与部分接收。
- 对接第三方患者信息来源，支持自动带入患者与申请信息。
- 预留临床侧“冰冻进度查看”接口占位，本阶段只保证常规主流程可用。

落地建议：

- 以 `Application` 为聚合入口，先建立标本生命周期主线。
- 所有状态变化必须附带时间节点、操作人和来源终端信息。
- 第三方患者信息对接优先做防腐层，不让外部字段直接渗透到领域模型。

完成标志：

- 从申请单创建到病理科接收可全程追踪。
- 每个标本都可查询当前状态、时间节点、操作人和轨迹。
- 接收环节可形成正式病理号并进入技术流程待办。

### M3. 技术组核心生产线

目标：

- 完成常规病理技术链路，形成从接收到玻片出片的可执行生产流程。

交付内容：

- 落地登记接收工作站、取材描写、脱水、包埋、常规切片、染色出片。
- 新增任务池、批次、篮筐、包埋盒、玻片、技术质控、回退重做等实体与状态机。
- 支持取材模板智能匹配、包埋盒预生成、切片备注、遗漏、跳号、重做提醒。
- 支持技术流程扫码流转、批量确认、拍照归档、超时提醒。
- 预留设备接入边界，打印机、打号机、高拍仪通过适配层接入，不直接耦合工作站逻辑。

落地建议：

- 所有技术任务统一进入任务池，通过状态机驱动流转，而不是工作站之间直接互调。
- 包埋盒和玻片必须能追溯上游标本和下游诊断使用情况。
- 回退重做必须保留原始记录，不允许覆盖历史处理痕迹。

完成标志：

- 接收病例可进入取材并一路流转到染色出片。
- 蜡块和玻片均可追溯来源标本、当前状态和操作记录。
- 重切、重包埋、退回重取等异常分支可闭环。

### M4. 医生组诊断与报告闭环

目标：

- 完成“分片 -> 诊断 -> 医嘱 -> 审核签发 -> 报告修订”的核心医疗价值闭环。

交付内容：

- 落地分片工作站、诊断平台、报告修改修订、医嘱工作站、科内会诊、质控评价。
- 新增诊断任务、报告、报告版本、签发流、会诊记录、医嘱、质控评分等实体。
- 支持初步、审核、签发三级权限，支持报告暂存、回退、拒签、延迟发布、修订留痕。
- 支持诊断时查看历史病理、标本信息、蜡块玻片信息、技术质控结果。
- 支持常规医嘱与特检医嘱下达，并把任务回流至技术组待办。

落地建议：

- 报告实体必须设计版本链，确保修订、回退和审计可追溯。
- 医嘱模型应区分常规医嘱与特检医嘱，但执行流转接口保持统一。
- 诊断工作台只消费聚合后的病例视图，不直接拼装底层多张表结构。

完成标志：

- 常规病例可形成正式报告并完成签发。
- 医嘱可从医生端下达到技术端并形成回传状态。
- 报告修订与会诊过程有完整审计链。

### M5. 归档、借记与科室运营支撑

目标：

- 补齐病理科日常运营所需的归档和物资管理能力。

交付内容：

- 落地申请单归档、蜡块归档、玻片归档、蜡块借记、玻片借记、归档柜管理、拍照归档。
- 落地试剂信息、试剂库存、仪器设备、维修保养记录。
- 建立归档位置、容量、借出归还、试剂阈值提醒、设备状态跟踪能力。
- 把蜡块或玻片归档位置信息回流给特检医嘱和诊断查询场景。

落地建议：

- 归档、借记、照片索引都必须绑定到统一病例主线。
- 物资与设备模块优先满足台账、预警和追踪，不在本阶段过度引入复杂采购流程。

完成标志：

- 任一玻片或蜡块可快速定位归档位置。
- 借出归还有完整记录并可追责。
- 试剂和设备有基础台账、阈值提醒和检索能力。

### M6. 集成、收费、历史数据与统计分析

目标：

- 让系统从“流程可用”升级到“可融入医院环境并支持管理决策”。

交付内容：

- 对接 HIS、EMR、LIS、PACS、收费系统，明确入参与回写边界。
- 对接标签打印机、玻片打号机、包埋盒打号机、高拍仪、病理摄像机等设备适配层。
- 建立历史报告导入能力和历史查询入口。
- 落地质控指标、管理指标、自定义统计报表与 Excel 导出。
- 建立接口重试、补偿、失败告警、对账机制。

落地建议：

- 所有外部系统与设备接入必须走独立适配层，并定义稳定的内部协议。
- 统计口径要先固化指标定义，再实现报表，避免开发中途口径漂移。
- 历史数据迁移优先保证“可查”，再逐步考虑深度结构化。

完成标志：

- 核心外部系统至少完成患者信息拉取、收费回写、历史报告查询三条主链路。
- 十三项病理质控指标可统计导出。
- 主要设备接入通过统一适配接口管理。

### M7. 试点上线与稳定化优化

目标：

- 在真实科室环境收口，完成首轮试点上线。

交付内容：

- 完成权限收敛、性能压测、异常兜底、日志监控、告警策略。
- 补齐培训材料、岗位 SOP、问题反馈闭环、灰度发布方案。
- 按角色完成护士、技师、医生、管理员试点验收。
- 对高频问题做二次优化，优先处理效率瓶颈和质控漏点。

落地建议：

- 试点阶段以“稳定运行”优先于“继续扩功能”。
- 每周输出问题清单、根因分类和修复节奏，用于快速迭代。
- 对异常高频节点保留人工兜底流程，避免试点中断。

完成标志：

- 常规病理主闭环可在试点科室连续运行。
- 关键岗位均有可执行操作手册。
- 主要异常场景有监控、有告警、有人工兜底方案。

## 7. 阶段验收测试基线

阶段验收建议固定覆盖以下场景：

- 正常主链路：申请创建、标本采集、接收、取材、切片、诊断、签发、归档全链路通过。
- 关键异常链路：拒收、部分接收、未固定提醒、漏扫、回退重取、重切、报告修订、医嘱终止。
- 权限测试：不同角色只能访问对应工作站和审批动作。
- 编码规则测试：病理号、标本号、蜡块号、玻片号在并发下唯一且可追溯。
- 集成测试：患者信息拉取、收费回写、历史数据导入、设备适配失败补偿。
- 统计测试：质控指标口径正确，导出结果可复核。
- 非功能测试：接口性能、任务并发、日志留痕、告警触发、数据审计。

## 8. 默认假设

- 当前以仓库现状为基础推进，主业务模块默认继续沉淀在 `bl-center`，不额外拆出新业务中心。
- 一期范围按“常规病理主闭环”规划，冰冻、细胞学、液基细胞学、免疫组化、分子病理优先作为 `M3-M6` 扩展能力逐步纳入，不要求首批同时全面上线。
- 本规划默认面向研发实施，因此优先按依赖顺序而不是按院内汇报口径排序。
- 每个里程碑周期为建议值，前提是有稳定的产品、业务和接口协同资源。

## 9. 推荐落地顺序与仓库映射

建议后续实施时按以下顺序推进仓库建设：

1. 在 `bl-center` 内扩展病理主线实体和应用服务。
2. 在 `bl-center` 内逐步补充接口层、应用层、领域层、基础设施层实现。
3. 在 `sql/` 中补充数据库设计与迁移脚本。
4. 在 `test/` 与 `bl-center/src/test` 中同步补齐里程碑级验收用例。
5. 当能力被两个及以上业务子域稳定复用后，再评估是否下沉到 `common/*` 或顶层 `infrastructure/*`。
